# 日志卷回收值班台

旧日志已删、日志卷仍然满——空间被"已删除但仍被进程打开"的文件占着。
本工具用 Flask 提供值班网页，从 `/proc` 盘点单个专用日志卷上的这类文件，
按进程组给出**达标且重启组数最少**的回收方案，并支持事后复核。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8080
```

容器启动时会运行 5 个样例日志进程（各自独立进程组），在命名卷 `/logs` 上制造
"已删除但仍被占用"的文件，可直接在网页上试演：

| 文件 | 大小 | 持有组 | 说明 |
|---|---|---|---|
| `api.log` | 40 MiB | 1 个组 | 独占 |
| `worker.log` | 30 MiB | 1 个组 | 独占，每秒再长 64 KiB（演示复核时"占用变化"） |
| `shared.log` | 50 MiB | **2 个组** | 必须同时重启两组才可回收 |
| `cache.log` | 8 MiB | 1 个组 | 独占 |

## 使用流程

1. **盘点**：点击"盘点日志卷"，页面列出卷上所有已删除但仍被打开的文件
   （按 `st_blocks` 已分配磁盘块估算，同一 inode 只计一次）及其全部持有进程组。
2. **生成方案**：勾选最多 12 个可重启的候选进程组，填要腾出的空间（MiB）。
   方案用**同一次盘点快照**计算：枚举候选子集，只有文件的**全部持有组**都被
   重启才计入可回收；给出达标且重启组数最少的方案，列出可回收文件与预计释放量。
   若全部候选组都重启也达不到目标，则报告最多可腾多少及对应文件。
3. **复核**：对方案点"复核"会**重新盘点**并比对。若方案涉及的文件消失、
   持有组或占用变化、原方案不再达标，或出现了**组数更少的达标方案**，
   则逐条指出变化并作废旧方案；其他无关变化以"提示"列出。

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 值班网页 |
| POST | `/api/inventory` | 重新盘点，返回快照 |
| GET | `/api/state` | 当前快照与方案列表 |
| POST | `/api/plan` | `{snapshot_id, groups[], target_bytes}` → 方案 |
| POST | `/api/review` | `{plan_id}` → 重新盘点并复核 |

## 并发与一致性

多次盘点/复核可以**同时进行**（扫描在锁外执行），一致性规则如下：

- 每次采集（普通盘点与复核的重新盘点）在**开始扫描前**领取一个全局递增的
  采集序号，新旧一律以"服务端开始采集的顺序"为准，与响应返回先后无关。
- 卷的**当前盘点**只接受最后开始的那次**成功**采集；更早开始、更晚返回的
  采集只会留档（其快照仍可被方案引用），不会把当前盘点顶回去。
- 每个方案各自只保留**本方案最后开始的那次成功复核**；别的采集更新卷的
  当前盘点，不影响任何方案自己的复核结论。
- 采集失败（如日志卷不可访问，返回 500）不改动任何已生效状态，其他成功
  采集照常生效。
- 网页对迟到响应做**单调合并**：盘点只接受序号更大的快照；方案列表只增
  不丢、同一方案的复核结论只接受序号更大的；复核详情面板同样不接受更旧
  的复核。因此已显示的盘点、方案列表、复核详情都不会因迟到响应倒退，
  被忽略的过期响应会在页面上给出提示。

## 对宿主机使用

把 compose 改为共享宿主机进程命名空间并挂载真实日志卷（见
`docker-compose.yml` 注释），并去掉样例进程。卷按"挂载点设备号"识别，
挂载的应是该专用卷的真实挂载点。

## 前提与限制

- 只处理**单个**专用日志卷（`LOG_VOLUME`，默认 `/logs`）。
- 假设所有持有进程的 fd 均可从 `/proc` 读取（容器内以 root 运行）；
  读不到的进程会被跳过，可能漏计持有组。
- 假设日志**不做内存映射**，故只扫描 fd，不处理 `mmap` 持有的已删除文件。
- 空间按 `st_blocks × 512` 估算（稀疏文件只计实际分配），与文件内容长度无关。
- 进程组按 PGID（`/proc/<pid>/stat`）划分；重启动作由值班员自行执行，
  本工具只给方案、不杀进程。
- 快照与方案保存在内存中，服务重启即清空。
- 候选组上限 12（枚举 2^12 个子集，结果确定）。
